# OpenMaster Helm chart

This production-oriented chart deploys the API, web server, three isolated Celery
workers, optional internal PostgreSQL/Redis/MinIO, ingress, migrations, NetworkPolicies,
HPA, and PDBs. It targets Kubernetes 1.26+ and k3s.

The chart never creates or embeds credentials. Every workload references the existing
Secret named by `externalSecrets.existingSecretName`. In production that Secret should
be generated by the Vault-backed `ClusterExternalSecret` documented in
`docs/deployment/vault-external-secrets.md`.

## Data-service modes

Each of `postgresql`, `redis`, and `minio` supports `enabled=true` for an internal
workload or `enabled=false` plus a required `externalHost` and configurable port for an
ExternalName Service. Persistent storage size and StorageClass are explicit. Internal
services are suitable for small installations, not automatic high availability.

External endpoints also require narrow destination CIDRs under
`networkPolicy.externalEgress`. Kubernetes NetworkPolicy is IP-based and cannot permit
an FQDN. There is intentionally no default `0.0.0.0/0` rule.

## Validation

```bash
helm lint helm/openmaster
deployment/scripts/validate-chart.sh
shellcheck deployment/scripts/*.sh
```

See `docs/deployment/` for k3s setup, Vault integration, production checks, and
troubleshooting.

For slow or multi-gigabyte source uploads,
`config.masteringAccessTokenTtlSeconds` controls how long the password proof remains
valid while the API receives the multipart body. The default is two hours; accepted
values range from 60 seconds to 24 hours.
